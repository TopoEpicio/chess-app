Architecture Review — Chess Training App

Deepening opportunities for testability and AI-navigability

Backend: FastAPI + SQLAlchemy + SQLite Frontend: React + TypeScript + Zustand + Stockfish WASM Domain: Chess Training (Puzzles, Repertoire, Analysis)

Executive Summary

The codebase has a clear feature-module structure (puzzles, repertoire, analysis, stats, openings) but most modules are shallow — their HTTP interface is nearly as complex as their implementation. Chess domain logic is duplicated across backend (Python) and frontend (TypeScript) with no shared domain model or seam. Frontend components couple directly to Zustand stores and the Stockfish WASM engine, making unit testing difficult. No adapter layer separates API clients, engine, or persistence from the components that use them.

Top candidates for deepening: (1) Puzzle Generation module — extract pure domain logic behind a seam; (2) Stockfish Engine Adapter — isolate UCI protocol from React lifecycle; (3) Repertoire Tree module — separate tree navigation from persistence/API.

Deepening Candidates

Puzzle Generation Module

Backend: puzzle_generator.py (430 lines) + puzzles.py router (187 lines)

Strong

Problem — Shallow Module, Leaky Seam

  • Interface ≈ Implementation: The router directly embeds category definitions (PUZZLE_CATEGORIES, PHASE_THEMES), SQL queries, and calls puzzle_generator.detect_tactical_moments(). Deleting the router would concentrate complexity — it is the complexity.
  • No seam between HTTP and domain: generate_puzzles_from_game endpoint mixes request parsing, DB lookups, game→moment detection, puzzle creation, and stats updating in one function.
  • Chess logic not testable in isolation: TacticalMoment, _detect_patterns, _calculate_difficulty, _build_solution_from_board are all private functions inside a single file. No interface to swap implementations (e.g., Stockfish-backed vs heuristic).
  • Duplicated domain: Frontend analysisEngine.ts re-implements detectTacticalPatterns, calculateDifficulty, detectPhase in TypeScript — same concepts, different code.

Solution — Deepen with a Domain Seam

  • Extract a PuzzleGenerator interface (protocol) with methods: generate_from_game(game_id), generate_from_fen(fen, move), categorize(puzzle).
  • Move all pure chess logic (_detect_patterns, _quick_eval, _calculate_difficulty, _detect_phase) into a ChessDomain module with no SQLAlchemy/FastAPI imports.
  • Router becomes a thin adapter: validates request → calls generator → persists results → returns DTO.
  • Define PuzzleCategory and Theme as domain types (in CONTEXT.md), not router-level constants.

Benefits — Locality & Leverage

  • Locality: Chess logic lives in one place (ChessDomain), not split across router + generator + frontend.
  • Leverage: Swap generator implementation (heuristic → Stockfish-backed) without touching router or tests.
  • Testability: Unit-test PatternDetector, DifficultyCalculator with pure FEN inputs — no DB, no HTTP, no React.
  • AI-navigability: Clear interface (PuzzleGenerator) documents the seam; an agent can implement a new generator without reading router code.

⚠ ADR Consideration

If an ADR mandates "all puzzle generation in Python," the Stockfish-backed generator would need a Python Stockfish wrapper (python-chess + stockfish binary). The seam still holds — just swap the implementation behind the protocol.

Stockfish Engine Adapter

Frontend: useStockfish.ts (274 lines) — mixes engine lifecycle, UCI parsing, multi-PV, React state

Strong

Problem — Engine Coupled to React Lifecycle

  • No seam: Components call deepAnalyze(fen) directly from the hook. The hook manages: script loading, engine process, UCI handshake, message parsing, multi-PV state, cancellation, and React state (ready, error, evalInfo).
  • Deletion test fails: Deleting the hook would scatter engine logic across every component that uses it (PuzzleSolver, Analysis, RepertoireViewer).
  • Untestable: Cannot unit-test explanation generation (analysisEngine.ts) without a real Stockfish WASM instance.
  • Leaky abstraction: deepAnalyze returns MultiPvLine[] but callers must know about pvCount, depth, UCI format details.

Solution — Engine Adapter with Pure Interface

  • Define EngineAdapter interface: analyze(fen, options): Promise, bestMove(fen): Promise, ready(): Promise.
  • Extract UCIProtocol module: pure functions parsing info depth X score cp Y multipv Z pv ... → structured data. No React, no WASM.
  • Implement StockfishWasmAdapter wrapping the WASM module. Keeps lifecycle (load, init, terminate) but delegates parsing to UCIProtocol.
  • Components depend on EngineAdapter (injected via context or prop), not the hook. Hook becomes a React adapter that provides the interface.

  • Interface = Test Surface: The EngineAdapter protocol documents exactly what callers need.

Repertoire Tree Module

Frontend: RepertoireViewer.tsx (552 lines) + repertoireStore.ts + tree components

Worth Exploring

Problem — Tree Logic Leaks Across Components

  • Viewer = Controller + View: RepertoireViewer handles: tree filtering (visibleNodes), path building (buildPathToNode), node selection, API calls (loadTree, linkOpeningToNode), Stockfish analysis trigger, import PGN parsing, quiz mode, breadcrumb rendering.
  • Store calls API directly: repertoireStore methods (loadTree, createNode, patchNode) call api.repertoire.* — no repository seam.
  • Duplicated tree logic: RepertoireTree, RepertoireBoardControls, RepertoireInfoPanel all derive paths/children from raw node array.
  • No domain type for "Repertoire": Just RepertoireNode[] array. Operations like "get main line", "get variations", "find transpositions" are re-implemented in each component.

Solution — Repertoire Domain Module + Repository Seam

  • Extract RepertoireTree domain type with methods: getMainLine(), getVariations(nodeId), getPathTo(nodeId), addVariation(parentId, moves[]), findTransposition(fen).
  • Define RepertoireRepository interface: getTree(repertoireId), saveNode(node), deleteNode(id). Store implements this; components depend on interface.
  • RepertoireViewer becomes a pure view component receiving RepertoireTree and Repository via props/context.
  • Move PGN import parsing to a PgnImporter adapter (already exists in backend; mirror on frontend or share via WASM).

Analysis Explanation Engine

Frontend: analysisEngine.ts (344 lines) — pure functions but no seam, duplicated from backend

Worth Exploring

Problem — Pure Functions Without a Seam

  • Good start: generateExplanation, detectTacticalPatterns, detectThreats, buildTopMoveExplanation are pure functions — no React, no side effects.
  • But no interface: Callers import functions directly. Cannot swap explanation strategy (e.g., "beginner" vs "advanced" coach) without changing imports.
  • Duplicated from backend: Same tactical patterns (fork, pin, skewer, hanging piece) implemented in puzzle_generator.py — two sources of truth.
  • Hard-coded Italian strings: Explanations embed Italian text ("Il tuo", "Minaccia", "FORZA!") — no i18n seam.

Solution — Explanation Engine with Strategy Seam

  • Define ExplanationEngine interface: explain(position, multiPv): ExplanationResult.
  • Extract ChessPatterns domain module (shared with puzzle generator) — single source of truth for fork/pin/skewer detection.
  • Implement StandardExplanationEngine, BeginnerExplanationEngine, CoachExplanationEngine as strategies.
  • Move localized strings to a MessageCatalog adapter (interface: t(key, params)).

API Client Adapter

Frontend: api/client.ts (125 lines) — hardcoded base URL, direct fetch, manual normalization

Speculative

Problem — No Seam Between Components and Network

  • Hardcoded configuration: API_BASE = 'http://localhost:8003/api' — no environment abstraction.
  • Normalization mixed with transport: normalizeStats, normalizeOpening live in the client. Components receive normalized data but have no control over it.
  • No interface: Stores (puzzleStore, repertoireStore) import api directly. Cannot test stores with a fake client without mocking fetch globally.
  • Error handling scattered: Each method throws raw Error; no unified ApiError type with status codes.

Solution — ApiClient Interface + Adapter

  • Define ApiClient interface with methods matching the current api object shape.
  • Implement FetchApiClient (current behavior) and MockApiClient (for testing).
  • Move normalization to a ResponseTransformer adapter (separate from transport).
  • Inject ApiClient into stores via constructor or context — stores depend on interface, not concrete fetch.

TOP RECOMMENDATION Puzzle Generation Module Deepening

Start with the Puzzle Generation module (Candidate #1). It has the strongest signal:

  • Deletion test passes decisively: Removing puzzles.py router would concentrate all puzzle logic into puzzle_generator.py — proving the router is a shallow adapter.
  • High leverage: The same chess logic is duplicated in the frontend (analysisEngine.ts). Deepening here creates a shared domain seam that pays off on both sides.
  • Clear domain vocabulary: CONTEXT.md (to be created) can define TacticalMoment, PuzzleTheme, DifficultyLevel, GamePhase — terms already used implicitly in code.
  • Testable immediately: Pure functions like _detect_patterns, _calculate_difficulty can be extracted and unit-tested with FEN fixtures today.
  • Enables future work: A PuzzleGenerator protocol makes it trivial to add a Stockfish-backed generator later (ADR-worthy but not blocking).

Proposed Domain Vocabulary (for CONTEXT.md)

TacticalMoment

A position + winning move + detected pattern (fork, pin, skewer, etc.) + solution line + difficulty + phase. Core output of puzzle generation.

PuzzleTheme

Canonical tactical motif: fork, pin, skewer, double_attack, checkmate, hanging_piece, discovered_attack.

DifficultyLevel

1–10 scale derived from theme base difficulty + solution length + capture presence. Used for filtering and progression.

GamePhase

opening | middlegame | endgame (plus specific endgame types). Determined by move count + material.

RepertoireTree

A rooted tree of RepertoireNodes with operations: main line, variations, path-to-node, transposition detection, add/remove variation.

EngineAdapter

Interface: analyze(fen, options), bestMove(fen), ready(). Implementations: StockfishWasmAdapter, RemoteEngineAdapter, MockEngineAdapter.

ExplanationEngine

Interface: explain(position, multiPv) → ExplanationResult. Strategies: Standard, Beginner, Coach. Uses ChessPatterns domain.

ChessPatterns

Pure domain module detecting tactical motifs from a position. Single source of truth shared by PuzzleGenerator and ExplanationEngine.

ApiClient / Repository

Interfaces separating transport (fetch, SQLAlchemy) from domain operations. Enables MockApiClient, InMemoryRepository for tests.
